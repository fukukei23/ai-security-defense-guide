02 実例 — IDOR発見と修正 — チェックリストを自アプリに当てたら穴が見つかった

3行で分かる

  1. ハードニング14項（個人適用セット）を reserve-optimizer（LINE Bot の予約管理アプリ）に適用点検したら、問診票が連番IDの走査で改ざんできる IDOR の穴を発見
  2. 予約IDの暗号論的ランダム化・存在検証・二重提出拒否の三層で塞いだ
  3. 全 1,489 テスト緑で本番反映（v32）まで完遂

対象アプリの構成

項目 内容
アプリ reserve-optimizer（クリニック向け LINE Bot 予約管理・個人開発・公開リポジトリ）
構成 LINE Messaging API + Google Apps Script（GAS）+ Cloudflare Worker + Stripe
データ 予約情報・問診票（健康状態等のセンシティブな回答）
特徴 個人開発のため WAF・SIEM・セキュリティチームは一切なし

まさに第1章で述べた「守りが薄い方」です。だからこそ、守れる範囲の防御を正しく入れる価値があります。

点検で発見した穴（IDOR）

チェックリスト項目3「サーバ側オブジェクト権限チェック」の判定で、次の設計上の穴が確定しました。

  • 予約IDが 連番（R0001、R0002、…）で生成されていた → 推測可能
  • 問診票を保存するAPIが、予約IDの存在検証をしていなかった → 存在しないIDも受け付けていた
  • かつ、既存の回答があれば 無条件に上書き していた

つまり、予約IDを1つずつずらして送り続ける（IDOR の典型的な列挙）ことで、他人の問診票の内容を読み取れる・書き換えられる状態でした。問診票は健康状態に関する回答を含むため、医療情報に準ずるデータです。

注意: IDOR（Insecure Direct Object Reference）は OWASP でも解説される一般的な脆弱性カテゴリです。連番のIDをずらしてアクセスする「列挙」はIDORの常套手段として広く知られており、AI自律攻撃の「列挙→悪用」連鎖（第2章参照）でも最初に試される類の穴です。つまり「攻撃者が見つけにくい穴」ではなく、自動化された攻撃が最初に通る穴でした。

before（穴のあった構造）:
  連番ID R0001 → API → 存在検証なし → 既存回答を無条件上書き

after（三層防御）:
  ① 予約IDを暗号論的ランダム化（R + UUID16桁）→ 列挙が不可能に
  ② 存在しない予約IDは拒否（Reservation not found）
  ③ 既存回答がある予約への二重提出は拒否

検討した選択肢と決定

案 内容 判定
A案（採用） 予約ID全モードで暗号論的ランダム化 + 存在検証 + 二重提出拒否。GAS側のみで完結・変更範囲が小さい ✅ 採用
B案（子タスク化） 予約作成時に intake トークンを発行し、フォームURL に添付する方式。より強固だが Worker・フロント・LINE文言まで波及 ⏳ 将来の補強として併存

A案の理由: 攻撃の成立条件（予約IDの推測可能性）を根本から断つため。二重提出拒否は「患者の再提出UX」との引き換えですが、医療情報の改ざん耐性を優先しました（再提出が必要な場合はクリニック側で対応する運用を想定）。

修正の実施（TDD）

テスト駆動で3つの修正を積み上げました。

修正 内容
F1: IDOR三層防御 予約IDの全モードランダム化（R + UUID16桁）・saveIntakeForm に存在検証と二重提出拒否を追加・エラー伝播の修正
F2: webhook ログの整理 webhook 本文をログに書かず長さのみ記録（シークレット/個人情報の非露出・項目13）
F3: 運用手順書の追記 トークンローテーション手順に URL 載せ制約と残存リスクを明記

検証結果: 全 1,489 テスト緑（run-all 1,425 + vitest 64・生 exit code 0 実測）で既存機能を壊さずに完了。GAS 本番に v32 として反映しました（デプロイ実測済み）。

点検プロセスで起きたこと（過程の記録）

  • 点検 → 発見 → 修正を1セッションで完遂: チェックリストを「読む」だけでなく「判定する」（○×を自分の実装で機械的に確認する）ことで、穴が見つかりました。「読んで満足」では発見できていませんでした
  • 発見の仕方: 「予約IDをサーバがどう生成しているか」「存在検証があるか」「上書きの条件は何か」をコードで一つずつ確認する、地味な照合の積み重ねです
  • 余波の発見: 点検過程で「本番の Cloudflare Worker がリポジトリのコードより古い」ことも判明（intake 転送が旧実装で・fail-closed エラー応答のためデータ書込は発生しない=危険なし・再デプロイを計画）

この実例から学べること

  1. チェックリストは「適用点検」して初めて効く: 14項を読むだけでは何も起きません。○×判定を自分のコードで確認したから、3項目目で穴が見つかった
  2. 個人開発にも「医療情報」はある: LINE Bot の問診票のように、個人開発アプリでもセンシティブなデータを扱う。守る対象の重要度で防御の優先度を決める
  3. AI自律攻撃に弱いのは列挙可能なID: 連番IDは自動化された攻撃が最初に通る穴。ランダム化は1行の変更ではありませんが、既存テストが緑のまま足せる修正で達成できる
  4. fail-closed は守りになる: Worker が古くても fail-closed エラー応答でデータ書込が発生しなかったのは結果的に安全でした。異常時に「開いたまま」より「閉じる」実装が効きます
