# 03 チェックリスト — 個人開発者が今日からやること

> **3行で分かる**
> 1. 個人開発アプリの防御は「全部は守れない」が前提
> 2. AI自律攻撃が最初に通る穴（列挙可能なID・認証なしのAPI・シークレット露出）から順に潰す
> 3. 今日から1時間で回せる優先順位付きチェックリストに整理した

---

## 優先順位付きチェックリスト

第3章の実例（IDOR発見）も踏まえ、**効いた順**に並べ替えた個人開発向けのリストです。上から順に。

### 🔴 最優先（今日やる・1〜2時間）

- [ ] **IDOR 封じ**: すべてのオブジェクトアクセス（ID付きのURL・API）で「このIDはこのユーザーのものか」を**サーバ側で検証しているか**。IDが連番・推測可能ならランダム化する（第3章参照）
- [ ] **シークレット非露出**: APIキー・トークン・個人情報がレスポンス・エラーメッセージ・ログに出ていないか。ログは「本文の長さだけ」記録するのが安全側
- [ ] **fail-closed の確認**: 認証失敗・予期しない入力のときに「閉じる（エラーで拒否）」実装になっているか。「とりあえず通す」実装は列挙攻撃の入り口

### 🟡 重要（今週やる）

- [ ] **レート制限**: ログイン・本人確認・フォーム送信など認証系のエンドポイントに速度制限を入れる（アプリ側で単純なカウンタでも効果あり）
- [ ] **認証状態遷移の再確認**: クライアントから送られてくる値（フラグ・状態・金額等）を鵜呑みにしていないか。遷移や権限はサーバ側で都度検証
- [ ] **資産棚卸し**: 公開しているURL・エンドポイント・デプロイ物を列挙し、忘れているものがないか。依存パッケージの既知脆弱性（n-day）を確認
- [ ] **二重送信の拒否**: フォーム系のAPIは「既に回答があれば拒否」を入れる（改ざん耐性が上がる・第3章の実測）

### 🟢 余裕があれば（今月中）

- [ ] **ログの保全と定期的な目視**: アクセスログを保持し、月1回「同一送信元の 401/403/404 大量」「深夜帯の異常な連続リクエスト」を目視する（行動ベース検知の個人版・第2章参照）
- [ ] **n-day パッチの仕組み化**: 依存パッケージの脆弱性情報を定期的に確認する仕組み（Dependabot 等）を入れる
- [ ] **MFA の適用範囲確認**: 管理UI・特権操作があるなら第二要素を要求する

> 💡 Tip: 「企業向け」の項目（WAF の行動モード・SIEM 相関・自動ブロック基盤・ネットワーク分離）は個人開発では再現できません。必要になったらすでに事業としての責任を持っている状態なので、その時にプロ向けの仕組み（Cloudflare WAF 等のサービス）を検討すれば十分です。

## 機械に任せられる部分

防御の定着は「人間の注意」より「仕組み」が確実です。

| 仕組み | 効くこと |
|---|---|
| gitleaks 等のシークレットスキャン（pre-commit） | APIキーの誤コミット（[セキュリティ基本ガイド](https://fukukei23.github.io/guides/security-basics/) 参照） |
| Dependabot / npm audit をCIに | n-day 高速パッチ（チェックリスト11） |
| テスト駆動開発 | 存在検証・二重提出拒否などの「拒否条件」を先にテストで書いてから実装する（第3章の実施方法） |
| デプロイ時のバージョン確認 | 「本番がリポジトリより古い」状態の検知（第3章の余波で実際に発見） |

## 最後に — 「読んだ」で終えない

第3章で記録した通り、チェックリストは「読んで満足」では何も起きません。○×判定を自分のコードで確認したからこそ、IDOR の穴が見つかりました。最初の1項目（IDOR 封じの確認）だけでも今日やってみてください。見つかったら、それは「事件が自分事になった」ということであり、見つからなければそれは「確認済み」という証跡です。どちらも価値があります。
